# Сервис асинхронной обработки платежей

Микросервис для асинхронной обработки платежей на FastAPI, Pydantic v2, SQLAlchemy 2, PostgreSQL, RabbitMQ/FastStream и Alembic. Создание платежа и запись события `payment.created` в outbox выполняются в одной транзакции базы данных. Фоновый relay публикует события из outbox в RabbitMQ, а один worker обрабатывает их, обновляет статус платежа и отправляет webhook.

## Архитектура

```text
Клиент -> FastAPI -> PostgreSQL (payments + outbox, одна транзакция)
                         ^                  |
                         |                  v
                    БД worker <- Outbox relay -> RabbitMQ -> обработчик платежей
                                                        |       |
                                                        |       +-> URL webhook
                                                        +-> повторная очередь -> DLQ
```

- Таблица `payments` хранит данные запроса, отпечаток для идемпотентности, статус обработки и состояние доставки webhook.
- Таблица `outbox` связывает транзакцию платежа с RabbitMQ. Доставка выполняется как минимум один раз, поэтому обработчик безопасно переносит повторные сообщения.
- RabbitMQ использует постоянные очереди, подтверждение публикации, не более одного обрабатываемого сообщения за раз, очередь повторных попыток и сохраняемую очередь `payments.dead` для сообщений, исчерпавших три попытки.
- Worker имитирует задержку шлюза 2–5 секунд и настраиваемую вероятность ошибки 10%.
- Webhook POST содержит событие, идентификатор и статус платежа, сумму, валюту и время обработки. Ошибки доставки повторяются через ту же очередь с экспоненциальной задержкой; число попыток хранится в БД. Идентификатор платежа передаётся в заголовке `Idempotency-Key`.

## Запуск через Docker Compose

```bash
cp .env.example .env
docker compose up --build
```

В PowerShell вместо первой команды выполни `Copy-Item .env.example .env`. Сначала запускается миграция базы данных, затем API и consumer. Документация API доступна по адресу <http://localhost:8000/docs>, панель RabbitMQ — <http://localhost:15672> (по умолчанию логин и пароль `payments`).

Для использования вне локальной разработки задай собственные значения `API_KEY`, пароля PostgreSQL и учётных данных RabbitMQ в `.env`. Если меняешь параметры PostgreSQL, обнови `DATABASE_URL`; если меняешь учётные данные RabbitMQ, обнови `RABBITMQ_URL`. Не добавляй `.env` в репозиторий.

## API

Для всех endpoint-ов требуется заголовок `X-API-Key`. При создании платежа также передаётся `Idempotency-Key`.

```bash
curl -i http://localhost:8000/api/v1/payments \
  -H 'Content-Type: application/json' \
  -H 'X-API-Key: local-development-key' \
  -H 'Idempotency-Key: order-2026-0001' \
  -d '{
    "amount": "1250.00",
    "currency": "RUB",
    "description": "Заказ 2026-0001",
    "metadata": {"order_id": "2026-0001"},
    "webhook_url": "https://example.com/payment-webhook"
  }'
```

Первый запрос возвращает `202 Accepted` с полями `payment_id`, `status` и `created_at`. Повторный запрос с тем же ключом и теми же данными возвращает существующий платёж (`200 OK`). Повторное использование ключа с другими данными возвращает `409 Conflict`.

```bash
curl http://localhost:8000/api/v1/payments/<payment_id> \
  -H 'X-API-Key: local-development-key'
```

Сначала статус платежа — `pending`; после обработки он меняется на `succeeded` или `failed`. Для проверки работоспособности есть `GET /health/live`; этот endpoint также требует `X-API-Key`.

## Доставка сообщений и обработка ошибок

Платёж и запись outbox сохраняются одной транзакцией, поэтому зафиксированный платёж не останется без события. Relay блокирует ещё не опубликованные записи через `SKIP LOCKED`, публикует постоянные сообщения с подтверждением RabbitMQ и отмечает их опубликованными. Если процесс упадёт после публикации, но до фиксации транзакции, сообщение может прийти повторно. Переходы статусов защищены от повторной обработки, а webhook получает ключ идемпотентности платежа. Гарантия доставки — как минимум один раз, а не строго однократная доставка.

Обработка платежа и доставка webhook получают до трёх попыток по умолчанию с задержками 1 и 2 секунды. Если попытки обработки платежа исчерпаны, его статус меняется на `failed`, после чего worker всё равно пытается отправить итоговый webhook. События, исчерпавшие попытки обработки или доставки webhook, сохраняются в DLQ для проверки или повторного запуска. Число попыток webhook хранится в БД и ограничивается параметром `RETRY_MAX_ATTEMPTS`. Получателю webhook следует устранять дубли по переданному идентификатору платежа в `Idempotency-Key`.

## Настройки

Полный список параметров приведён в `.env.example`. `PAYMENT_FAILURE_RATE` задаёт вероятность имитации ошибки шлюза; `PAYMENT_MIN_DELAY_SECONDS` и `PAYMENT_MAX_DELAY_SECONDS` задают задержку обработки. `OUTBOX_POLL_INTERVAL_SECONDS` и `OUTBOX_BATCH_SIZE` настраивают частоту опроса и размер пакета outbox.
